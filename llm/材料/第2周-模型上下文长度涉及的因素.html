第 2 周：模型上下文长度涉及的因素

对应日常问题：Ollama 为何能设上下文？出厂 256K 运行时能不能小于等于 256K？厂商为何不直接标 512K / 1M？底层难点是什么？
本仓库对照：models/SmolLM2-135M/config.json 里 max_position_embeddings = 8192。

入口：材料索引 · 学习计划 · 第2周 Auto 工厂

1. 两套「长度」不要混

训练 / 出厂上限 运行时上下文（如 Ollama num_ctx）
是什么 位置编码按多长设计、长文续训保证到多长 这次推理 KV 缓存开多大
写在哪 config.json 的 max_position_embeddings 等 启动参数、Modelfile
能不能改 改它不等于重新训出更长能力 每次运行可改，主要影响内存
SmolLM2 8192 应 ≤ 8192 才是原汁原味

训练时定下来的是「最长能看多远」的质量上限，不是每次必须用满的长度。注意力只对当前这段 input_ids 计算。你只塞 512 个 token，模型就只看这 512 个。

出厂窗口（如 256K 或本仓库 8192）
    = 厂家保证「在这个长度内按设计工作」

Ollama / 部署 num_ctx
    = 这次对话准备多大的序列缓冲（越长越吃 KV cache）

2. 训练时谁决定上下文上限

核心：模型在训练里 真的按多长的序列算过注意力、位置编码按多长设计。

因素 起什么作用
训练序列长度 数据 pack 成 4K / 32K / 256K，模型才有机会学这个距离上的关系
位置编码 学习式位置表：表有多长，上限就多硬。RoPE：按某个长度训，rope_theta 配合长文；再长是外推
max_position_embeddings 结构门牌上的设计上限
注意力实现 全量注意力大约随长度平方涨；长窗要 Flash Attention、分组 KV、滑动窗口等才能训得动
续训 / 加长 很多「256K 出厂」是先短窗预训练，再在长文本上继续训或做 YaRN 等

出厂 256K ≈ 保证规格，不是物理定律。

3. 运行时怎么设（256K 出厂为例）

可以、也应该：运行上下文 ≤ 出厂窗口。 设小一点只是少占 KV 缓存，模型还能跑。

实际能用的上下文 ≈ min(
    出厂窗口（如 256K）,
    你设置的 num_ctx / max_seq,
    显存装得下的 KV cache
)
做法 是否推荐 说明
小于 256K 对 正常部署，省内存
等于 256K 对 用满出厂规格（硬件要扛得住）
大于 256K 不按规格保证 有的框架报错；有的 RoPE 缩放硬拉。那是外推，长距离易糊、丢前面、乱编

消费级卡就算标了 256K，也可能只能开 32K/64K，因为显存先爆。

记一句：出厂长度是质量上限；运行时只能往下减来省内存，不要当可以随便往上加的旋钮。

4. 厂商为什么不直接标 512K / 1M

不是不想印卖点，而是 按 1M 认真训、认真保证质量 代价按长度猛涨，而且常出现「塞得进、用不好」。

难点 一句话
平方级算力 标准注意力两两配对，长度 ×32，这一项大约 ×1000 量级
显存 训练要激活；推理要 KV cache，长度线性涨但系数很大
长程数据 缺的是「远距离真相关」的语料，不是磁盘上很长的字符串
「真的能用」 softmax 稀释、Lost in the Middle、梯度传不远；捞针 ≠ 跨章节推理

产品上多数请求只要几千到几万 token。为顶部 1% 超长文档把所有人成本和延迟拉高，不划算。常见做法：标一个够用的窗口 + RAG 处理整本书。

加长的技术（滑动窗口、GQA/MLA、SSM、线性注意力）是在 用近似换长度，长距离精度会打折。把 config 改成 1M 只改了门牌。

5. 底层原因：四件事其实是一条因果链

根因：Transformer 用「每个位置看所有前面的位置」建模长距离关系。 长度一拉，计算、内存、数据和学习信号一起变差。

「每个位置看所有历史」
    → 配对次数 ~ n²            （算力）
    → 要存所有历史的 K/V       （推理显存）
    → 反传还要激活             （训练显存）
    → 需要「远距离真相关」的数据（数据没有那么多）
    → softmax 稀释 + 梯度太远   （即便训了也不稳）

5.1 平方级算力：为什么是 n²

注意力要决定「该看谁」，就要和序列里每一个位置比相关性。长度 (n) 时大约 (n \times n) 对。Causal LM 是下三角，仍是 (\frac{n(n+1)}{2})，数量级还是 (n^2)。

(n) 从 8K 到 256K（32 倍），这一项大约 1000 倍，再乘层数、头数、batch。
底层：关系被定义成两两配对。要降复杂度只能少配对（局部/稀疏/线性注意力）。

5.2 显存：推理 KV + 训练激活

推理（Ollama 等）——KV cache

生成时不能每步把前文重算一遍，于是存每个已出现 token 的 Key、Value。每多一个 token 就多一行。

KV ≈ 层数 × 长度 × KV头数 × 头维度 × 2(K和V) × 字节数

长度 ×2，缓存 ×2。对长度是 线性，但层多、FP16 时 256K 就能撑满一张卡。
底层：用空间换时间——记住过去所有向量，才能续写。

训练——激活

反传要知道中间层当时的样子。大约 层数 × batch × n × hidden_size，有的实现还涉及 (n \times n) 分数（或重算以省显存）。
底层：链式法则沿整条计算图往回走，图随 (n) 变长。

5.3 长程数据：缺的不是很长的字符串

训练要的是：在距离很远时，后面的词真的依赖前面的信息（第 2 页的约束到第 400 页还管用）。

  • 网页、对话、多数书，有用依赖多在几千 token 内；
  • 把短文拼成 1M，模型看见的是互不相干的片段，学的是局部续写；
  • 真·长程标注极贵、极少。

底层：自然语言统计以短程为主；超长、可检验的依赖是稀有事件。只预测下一个 token，不会自动逼模型去用 20 万字之前的一个数字。

5.4 「真的能用」：长距离查找不稳定

  • 注意力被稀释： softmax 在 (n) 个分数上分配权重，(n) 越大，真正相关的位置分到的质量越小。
  • Lost in the Middle： 更吃开头和结尾，中间段落像没看见。
  • 信用分配太远： 很早的 token 要经过上万步生成才体现对错，梯度又小又噪。
  • 评测 ≠ 产品： 大海捞针能过，不等于跨章节推理、法律、代码库级别「真的能用」。

6. 速记

  1. 出厂窗口 = 训练保证的上限；运行 num_ctx = 这次 KV 开多大，应 ≤ 上限。
  2. 本仓库 SmolLM2：max_position_embeddings = 8192。
  3. 加长的难点：(n^2) 算力、KV/激活显存、没有足够的长程数据、softmax 稀释与远距离梯度。
  4. 正路：改配对方式、压缩 KV、RAG；不要指望只改 config。
