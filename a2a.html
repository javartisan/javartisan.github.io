1. 简介

Agent2Agent（A2A）协议是一种开放协议，用于实现 AI Agent 之间的通信与协作。 该协议定义了一套标准化方式，使不同框架、不同供应商或不同实现方式构建的 Agent 能够相互发现、交换信息、管理任务，并协同完成复杂工作。

1.1 A2A 的关键目标

A2A 的主要目标包括：

  • 实现不同 AI Agent 之间的互操作性。
  • 支持 Agent 能力发现。
  • 支持同步、异步和流式通信。
  • 支持多轮交互和长时间运行的任务。
  • 支持任务状态管理。
  • 支持结构化数据、文件及其他类型内容的交换。
  • 支持多种协议绑定方式。
  • 提供标准化的认证、授权和安全机制。

1.2 指导原则

A2A 协议遵循互操作性、可扩展性、协议独立性和实现灵活性等原则。 协议定义核心语义，而具体的传输方式可以通过不同的协议绑定实现。

1.3 规范结构

本规范定义 A2A 的核心概念、操作、数据模型、协议绑定、安全要求以及 Agent 发现机制。

1.4 规范性内容

规范中使用的 MUST、MUST NOT、 REQUIRED、SHALL、SHALL NOT、 SHOULD、SHOULD NOT、 RECOMMENDED、NOT RECOMMENDED、 MAY 和 OPTIONAL 等术语用于表示不同级别的规范要求。

2. 术语

2.1 需求语言

本规范中的规范性关键字按照 RFC 2119 和 RFC 8174 所定义的方式解释。

2.2 核心概念

Agent

能够代表用户或系统执行任务的软件实体。Agent 可以接收请求、处理任务、生成结果， 并与其他 Agent 进行交互。

Client

发起 A2A 请求的一方。Client 可以是另一个 Agent，也可以是应用程序或服务。

Server

提供 A2A 服务并处理请求的一方。

Task

表示一个可管理的工作单元。Task 可以具有生命周期和状态，并可以随着执行过程不断更新。

Context

用于关联多个相关任务或多轮交互的上下文标识。

Message

Agent 或 Client 之间交换的信息单元。

Artifact

任务执行过程中生成的结果或输出，例如文本、文件或结构化数据。

Part

消息或 Artifact 的组成部分，可以表示不同类型的数据内容。

3. A2A 协议操作

3.1 核心操作

3.1.1 发送消息（Send Message）

Client 向 Agent 发送消息，并等待服务器返回结果。 返回结果可以是消息，也可以是任务。

3.1.2 发送流式消息（Send Streaming Message）

Client 向 Agent 发送消息，并通过流式方式持续接收任务状态更新、Artifact 更新 或其他事件。

3.1.3 获取任务（Get Task）

根据任务标识获取指定任务的当前状态和相关信息。

3.1.4 列出任务（List Tasks）

查询符合指定条件的任务集合，并支持分页。

3.1.5 取消任务（Cancel Task）

请求取消一个正在执行的任务。

3.1.6 订阅任务（Subscribe to Task）

订阅指定任务的后续更新。

3.1.7 创建推送通知配置

为任务创建推送通知配置，使服务器能够主动向指定地址发送任务更新。

3.1.8 获取推送通知配置

获取指定任务的推送通知配置。

3.1.9 列出推送通知配置

获取任务关联的所有推送通知配置。

3.1.10 删除推送通知配置

删除指定的推送通知配置。

3.1.11 获取扩展 Agent Card

获取需要认证或授权后才能访问的扩展 Agent Card。

3.2 操作参数对象

3.2.1 SendMessageRequest

表示发送消息操作的请求对象，包含需要发送的消息以及可选配置。

3.2.2 SendMessageConfiguration

定义发送消息时的配置选项，例如历史记录长度、流式行为和其他服务参数。

3.2.3 流式响应

流式操作允许服务器在任务执行过程中持续返回状态更新和 Artifact 更新。

3.2.4 历史记录长度语义

历史记录长度用于控制响应中返回多少历史消息或相关上下文。

3.2.5 元数据

元数据用于传递协议未明确标准化的附加信息。

3.2.6 服务参数

服务参数用于传递与具体服务实现相关的配置或信息。

3.3 操作语义

3.3.1 幂等性

协议中的操作应根据其定义遵循相应的幂等性要求。 Client 在重试请求时需要理解操作是否可能导致重复执行。

3.3.2 错误处理

服务器在无法成功处理请求时，应返回符合协议定义的错误信息。 错误信息应能够帮助 Client 理解请求失败的原因。

3.3.3 异步处理

对于长时间运行的操作，服务器可以返回一个 Task， Client 可以通过查询、订阅、流式通信或推送通知获取后续更新。

3.3.4 能力验证

Client 在调用特定功能之前，应根据 Agent Card 中声明的能力确认服务器是否支持相应操作。

如果 Client 请求服务器未声明支持的功能，服务器可以拒绝该请求并返回相应错误。

3.4 多轮交互

3.4.1 Context 标识符语义

Context ID 用于关联属于同一上下文的多个任务或多轮交互。

3.4.2 Task 标识符语义

Task ID 用于唯一标识一个任务。 同一个 Context 可以包含多个 Task。

3.4.3 多轮对话模式

A2A 支持在已有上下文中继续交互，也支持围绕已有 Task 继续提供信息或处理后续请求。

4. 协议数据模型

4.1 核心对象

4.1.1 Task

Task 表示由 Agent 执行的工作单元。 Task 可以包含以下信息：

  • 任务标识符。
  • 上下文标识符。
  • 任务状态。
  • 任务历史消息。
  • 任务生成的 Artifact。
  • 元数据。

4.1.2 TaskStatus

TaskStatus 表示任务当前状态，并可以包含状态消息和时间相关信息。

4.1.3 TaskState

任务状态可以包括：

  • submitted：已提交。
  • working：正在处理。
  • input-required：需要输入。
  • auth-required：需要认证。
  • completed：已完成。
  • canceled：已取消。
  • failed：失败。
  • rejected：被拒绝。

4.1.4 Message

Message 表示 Client 与 Agent 之间交换的消息。 消息包含发送方角色以及一个或多个 Part。

4.1.5 Role

Role 用于表示消息发送方的角色，例如用户或 Agent。

4.1.6 Part

Part 用于表示消息或 Artifact 中的具体内容。 不同类型的 Part 可以用于承载文本、文件、结构化数据等。

4.1.7 Artifact

Artifact 表示任务执行过程中生成的输出。 一个任务可以生成一个或多个 Artifact。

4.2 流式事件

4.2.1 TaskStatusUpdateEvent

用于通知 Client 任务状态发生变化。

4.2.2 TaskArtifactUpdateEvent

用于通知 Client 任务产生了新的 Artifact 或已有 Artifact 发生更新。

4.3 推送通知对象

4.3.1 PushNotificationConfig

定义服务器向 Client 主动发送任务更新时使用的配置。

4.3.2 AuthenticationInfo

定义推送通知过程中可能需要使用的认证信息。

4.3.3 推送通知载荷

推送通知载荷用于传递任务状态或任务更新信息。

4.4 Agent 发现对象

4.4.1 AgentCard

Agent Card 是描述 Agent 身份、能力、接口和服务信息的核心发现对象。

4.4.2 AgentProvider

AgentProvider 描述 Agent 的提供方信息。

4.4.3 AgentCapabilities

用于声明 Agent 支持的能力，例如流式响应、推送通知和其他功能。

4.4.4 AgentExtension

用于声明 Agent 支持的扩展能力。

4.4.5 AgentSkill

AgentSkill 用于描述 Agent 可以执行的具体技能或能力。

4.4.6 AgentInterface

描述 Agent 支持的协议接口和对应的服务端点。

4.4.7 AgentCardSignature

用于对 Agent Card 进行签名，以支持身份验证和完整性校验。

5. 协议绑定要求与互操作性

5.1 功能等价要求

不同协议绑定应尽可能提供与 A2A 核心协议一致的功能语义。

5.2 协议选择与协商

Client 可以根据 Agent Card 中声明的接口选择适合的协议进行通信。

5.3 方法映射参考

不同协议绑定需要将 A2A 的核心操作映射为对应传输协议中的方法或接口。

5.4 错误代码映射

不同传输协议的错误表示方式需要映射到 A2A 定义的错误语义。

5.5 JSON 字段命名约定

JSON 表示中的字段名称应遵循协议规定的命名约定。

5.6 数据类型约定

不同协议绑定需要保持数据类型语义的一致性。

5.6.1 时间戳

时间戳应按照协议规定的标准格式进行表示。

5.7 字段存在性与可选性

协议绑定必须正确表达字段是必填、可选还是未提供。

5.8 自定义绑定标识

自定义协议绑定应提供明确的标识，以便 Client 能够识别和选择该绑定。

6. 常见工作流与示例

6.1 基本任务执行

Client 向 Agent 发送消息。Agent 可以立即返回结果，也可以创建一个 Task 并返回任务状态。

6.2 流式任务执行

Client 使用流式操作发送请求，服务器在任务执行期间持续返回状态更新和结果更新。

6.3 多轮交互

Client 可以使用 Context ID 或 Task ID 继续之前的交互。

6.4 版本协商错误

当 Client 和 Server 无法协商兼容的协议版本时，应返回相应的版本错误。

6.5 任务列表与管理

Client 可以按照 Context、任务状态或其他条件查询任务，并支持分页获取结果。

6.6 推送通知的设置与使用

Client 可以为任务配置推送通知地址。当任务状态发生变化时， Server 可以主动向指定地址发送更新。

6.7 文件交换（上传与下载）

A2A 支持在消息或 Artifact 中交换文件。 文件可以通过协议支持的方式直接传输或通过引用方式访问。

6.8 结构化数据交换

A2A 支持在 Agent 之间交换结构化数据。

6.9 获取经过认证的扩展 Agent Card

对于包含受保护信息的 Agent Card，Client 可能需要先完成认证， 然后才能获取扩展 Agent Card。

7. 认证与授权

7.1 协议安全

A2A 通信应采用适当的安全机制保护数据传输、身份和访问权限。

7.2 Server 身份验证

Client 应能够验证其通信目标 Server 的身份。

7.3 Client 认证过程

Client 根据 Server 声明的安全要求提供相应凭据。

7.4 Server 认证职责

Server 负责验证 Client 提供的认证信息。

7.5 Server 授权职责

Server 负责确定经过认证的 Client 是否具有访问请求资源或执行请求操作的权限。

7.6 任务内授权

某些任务在执行过程中可能需要额外的授权。 协议支持在任务生命周期内处理此类授权需求。

7.6.1 任务内授权 Agent 职责

Agent 在需要授权时，应通知 Client 当前任务需要进一步认证或授权。

7.6.2 任务内授权 Client 职责

Client 负责根据要求完成授权流程，并向 Agent 提供继续任务所需的信息。

7.6.3 任务内授权安全注意事项

授权流程应避免泄露敏感凭据，并应使用安全的认证和授权机制。

7.6.4 任务内授权范围

授权信息应限制在执行当前任务所需的最小权限范围内。

8. Agent 发现：Agent Card

8.1 目的

Agent Card 用于让 Client 发现 Agent，并了解其身份、能力、技能、 接口、安全要求以及其他服务信息。

8.2 发现机制

Client 可以通过协议定义的发现机制获取 Agent Card。

8.3 协议声明要求

8.3.1 支持的接口声明

Agent 应在 Agent Card 中声明其支持的接口和协议绑定。

8.3.2 Client 协议选择

Client 根据 Agent Card 中声明的接口选择兼容的协议进行通信。

8.4 Agent Card 签名

Agent Card 可以进行数字签名，以确保内容完整性并支持身份验证。

8.4.1 规范化要求

在签名前，需要按照定义的规则对 Agent Card 内容进行规范化处理。

8.4.2 签名格式

签名应使用协议定义的格式表示。

8.4.3 签名验证

Client 可以使用签名信息验证 Agent Card 的完整性和来源。

8.5 Agent Card 示例

Agent Card 用于描述 Agent 的基本信息、能力、技能、支持的接口和安全方案。

8.6 缓存

8.6.1 Server 要求

Server 应提供适当的信息，使 Client 能够合理缓存 Agent Card。

8.6.2 Client 要求

Client 可以根据缓存策略缓存 Agent Card，并在必要时重新获取最新版本。

9. JSON-RPC 协议绑定

9.1 协议要求

JSON-RPC 绑定使用 JSON-RPC 协议承载 A2A 操作。

9.2 服务参数传输

服务参数按照 JSON-RPC 绑定定义的方式传输。

9.3 基础请求结构

请求应符合 JSON-RPC 定义的基本请求结构，并包含对应的 A2A 方法和参数。

9.4 核心方法

  • SendMessage：发送消息。
  • SendStreamingMessage：发送流式消息。
  • GetTask：获取任务。
  • ListTasks：列出任务。
  • CancelTask：取消任务。
  • SubscribeToTask：订阅任务。
  • 推送通知配置方法。
  • GetExtendedAgentCard：获取扩展 Agent Card。

9.5 错误处理

A2A 错误语义应映射为 JSON-RPC 错误响应。

10. gRPC 协议绑定

10.1 协议要求

gRPC 绑定使用 gRPC 服务定义实现 A2A 协议操作。

10.2 服务参数传输

服务参数根据 gRPC 的数据模型和协议定义进行传输。

10.3 服务定义

A2A 定义相应的 gRPC 服务和方法，用于实现协议中的核心操作。

10.4 核心方法

  • SendMessage
  • SendStreamingMessage
  • GetTask
  • ListTasks
  • CancelTask
  • SubscribeToTask
  • CreateTaskPushNotificationConfig
  • GetTaskPushNotificationConfig
  • ListTaskPushNotificationConfigs
  • DeleteTaskPushNotificationConfig
  • GetExtendedAgentCard

10.5 gRPC 特定数据类型

10.5.1 TaskPushNotificationConfig

定义 gRPC 绑定中使用的任务推送通知配置对象。

10.6 错误处理

A2A 错误应映射为适当的 gRPC 状态和错误信息。

10.7 流式处理

gRPC 流式机制可用于持续传递任务状态和 Artifact 更新。

11. HTTP+JSON/REST 协议绑定

11.1 协议要求

HTTP+JSON/REST 绑定通过 HTTP 请求和 JSON 数据表示 A2A 操作。

11.2 服务参数传输

服务参数根据 HTTP 请求的定义进行传递。

11.3 URL 模式和 HTTP 方法

11.3.1 消息操作

定义用于发送消息和流式消息的 URL 模式和 HTTP 方法。

11.3.2 任务操作

定义获取、查询、取消和订阅任务所使用的 HTTP 接口。

11.3.3 推送通知配置

定义管理推送通知配置的 HTTP 接口。

11.3.4 Agent Card

定义获取 Agent Card 和扩展 Agent Card 的 HTTP 接口。

11.4 请求与响应格式

请求和响应使用 JSON 格式，并遵循 A2A 数据模型。

11.5 请求参数的查询参数命名

通过查询参数传递的请求参数应遵循协议规定的命名规则。

11.6 错误处理

A2A 错误应映射为相应的 HTTP 状态码和错误响应。

11.7 流式处理

HTTP 绑定支持按照定义的流式机制传递任务更新。

12. 自定义绑定指南

12.1 绑定要求

自定义协议绑定必须保持 A2A 核心操作和数据模型的语义一致性。

12.2 数据类型映射

A2A 数据类型需要正确映射到自定义协议的数据类型。

12.3 服务参数传输

自定义绑定需要定义服务参数的传输方式。

12.4 错误映射

自定义协议错误需要映射为 A2A 兼容的错误语义。

12.5 流式支持

如果协议支持流式通信，自定义绑定应提供与 A2A 流式语义一致的实现。

12.6 认证与授权

自定义绑定应支持 A2A 定义的认证和授权要求。

12.7 Agent Card 声明

自定义绑定应在 Agent Card 中明确声明。

12.8 互操作性测试

实现方应测试自定义绑定与其他 A2A 实现之间的互操作性。

13. 安全注意事项

13.1 数据访问与授权范围

系统应确保 Agent 只能访问其被授权访问的数据和资源。

13.2 推送通知安全

推送通知端点需要进行适当保护，以防止未经授权的访问或伪造请求。

13.3 扩展 Agent Card 访问控制

扩展 Agent Card 中可能包含受保护信息，因此应实施适当的访问控制。

13.4 通用安全最佳实践

实现 A2A 协议时，应遵循安全通信、身份认证、最小权限原则、 输入验证以及敏感信息保护等通用安全最佳实践。

14. IANA 注意事项

14.1 媒体类型注册

14.1.1 application/a2a+json

定义 A2A JSON 数据的媒体类型。

14.2 HTTP 请求头字段注册

14.2.1 A2A-Version 请求头

用于在 HTTP 通信中传递 A2A 协议版本信息。

14.2.2 A2A-Extensions 请求头

用于声明或传递所使用的 A2A 扩展信息。

14.3 Well-Known URI 注册

A2A 定义用于 Agent 发现的标准 Well-Known URI。

附录 A：迁移与旧版兼容性

A.1 旧版文档锚点

为了兼容旧版文档引用，规范提供旧版锚点或对应关系。

A.2 迁移指南

实现从旧版本迁移到当前版本时，应根据规范中的兼容性要求进行调整。

A.2.1 破坏性变更：移除 Kind 判别字段

当前版本移除了旧版本中用于区分对象类型的 kind 判别字段。 实现方需要根据新的数据模型调整对象类型识别方式。

A.2.2 破坏性变更：扩展 Agent Card 字段位置调整

扩展 Agent Card 的相关字段位置发生调整。 实现方需要更新 Agent Card 的生成和解析逻辑。

A.3 未来自动化

未来版本可能进一步提供工具支持，以帮助实现版本迁移和兼容性处理。

附录 B：与 MCP（模型上下文协议）的关系

A2A 与 MCP 解决的是不同层面的互操作问题。

MCP 主要用于为 AI 模型或 Agent 提供访问工具、资源和上下文的标准化方式。

A2A 则主要用于 Agent 与 Agent 之间的通信、任务协作和能力发现。

两种协议可以组合使用：Agent 可以通过 MCP 使用工具和资源， 同时通过 A2A 与其他 Agent 协作。
