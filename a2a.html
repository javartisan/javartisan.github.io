Agent2Agent (A2A) 协议规范

最新发布版本：1.0.0｜翻译自官方：a2a‑protocol.org/latest/specification

重点章节：3.3.4 能力校验 Capability Validation

1. 简介

Agent2Agent（A2A）协议是一套开放标准，用于实现相互独立、内部实现不透明的AI Agent系统之间通信与互操作。在Agent生态中，各个Agent可能基于不同框架、不同编程语言、由不同厂商开发；A2A提供一套公共交互语言与交互模型。

本文档为A2A协议完整技术规范。协议主要目标是让Agent可以完成以下能力：

  • 互相发现对方具备的能力；
  • 协商交互模式（文本、文件、结构化数据）；
  • 管理协同任务；
  • 安全交换信息，共同完成用户目标，不需要访问彼此的内部状态、记忆或者工具。

1.1 A2A 核心目标

  • 互操作性：打通不同Agent系统之间的通信壁垒。
  • 协同能力：支持Agent之间任务委派、交换上下文，协同处理复杂用户请求。
  • 能力发现：Agent可以动态查找并理解其他Agent具备的能力。
  • 灵活性：支持多种交互模式：同步请求‑响应、实时流式输出、长耗时任务的异步推送通知。
  • 安全性：面向企业环境的安全通信范式，复用成熟Web安全最佳实践。
  • 异步优先：原生支持长耗时任务以及需要人工介入（人在回路）的交互场景。

1.2 设计指导原则

  • 简洁：复用已经成熟通用标准（HTTP、JSON‑RPC 2.0、SSE服务器推送事件）。
  • 企业就绪：对齐企业级实践，覆盖认证、鉴权、安全隐私、链路追踪、监控。
  • 异步优先：专为可能耗时极长的任务、人工介入交互场景设计。
  • 媒介无关：支持多种内容交换：文本、音视频（文件引用）、结构化数据表单，甚至可以嵌入UI组件。
  • 执行黑盒：Agent协作只依赖对外声明的能力与交换的信息，不需要共享内部思考过程、执行计划、工具实现细节。

1.3 规范分层结构

整个规范分为三层，三层协同构成完整协议定义：

  1. 第一层：标准数据模型：定义所有A2A实现必须理解的核心数据结构、消息格式，与传输协议无关，使用Protocol Buffer定义。
  2. 第二层：抽象操作：描述A2A Agent必须实现的基础能力与行为，不绑定底层传输协议。
  3. 第三层：协议绑定：把抽象操作、数据模型映射到具体传输实现：JSON‑RPC、gRPC、HTTP/REST；定义方法名、接口路径以及协议特有行为。
分层的好处：核心语义在所有协议绑定中保持一致；新增传输绑定不需要改动底层数据模型；开发者可以独立理解业务操作，不用关心传输细节；依靠统一标准数据模型保证跨实现互操作。

1.4 规范性内容

除本文档协议要求外，spec/a2a.proto 是全部协议数据对象、请求响应消息的唯一权威规范性源文件。构建时会自动生成JSON产物 spec/a2a.json，该文件仅用于工具辅助，不属于规范本体。所有SDK、Schema、衍生代码必须从proto文件编译生成，禁止手动修改。

变更控制与弃用生命周期

  • proto消息/字段重命名时，保留旧字段标记为已弃用，直到下一个大版本才彻底移除。
  • 发生破坏性重大变更，必须附带迁移指引文档。
  • 保留旧文档锚点，防止外部链接失效。
  • SDK与JSON Schema应提供弃用别名保证向后兼容。
  • 被弃用字段，至少要等到引入该变更后的下一个主版本，才允许删除。

2. 术语定义

2.1 要求关键字说明

文档中 MUST(必须)、MUST NOT(严禁)、REQUIRED(必填)、SHALL(应当)、SHALL NOT(禁止)、SHOULD(建议)、SHOULD NOT(不建议)、RECOMMENDED(推荐)、MAY(可选)、OPTIONAL(可选)，遵循 RFC 2119 的语义。

2.2 核心概念

名词释义
A2A ClientA2A客户端，代表用户或者其他系统，向A2A服务端发起请求的应用/Agent。
A2A Server(Remote Agent)A2A服务端（远端Agent），暴露A2A兼容接口，处理任务并返回响应的Agent系统。
Agent CardJSON元数据文档，由A2A服务端对外发布，描述Agent身份、能力、技能、服务接口地址、鉴权要求。
Message 消息客户端与远端Agent之间一轮通信单元；包含role角色，由一个或多个Part内容片段组成。
Task 任务A2A管理的基础工作单元，拥有唯一ID，有状态，具备完整生命周期。
Part 片段Message或者Artifact内部最小内容单元，可以是文本、文件引用、结构化数据。
Artifact 产物Agent执行任务产出输出（文档、图片、结构化数据），由多个Part构成。
Streaming 流式任务状态变更、产物分片增量实时推送，依靠传输层流式机制实现。
Push Notification 推送通知服务端主动向客户端Webhook地址发送HTTP POST异步任务更新，适用于长耗时、客户端无长连接场景。
Context 上下文可选标识符，逻辑上将一批相关Task、Message归为一组。
Extension 扩展在A2A核心规范之外，Agent提供额外功能与数据的扩展机制。

3. A2A协议操作

本章以传输无关的方式描述A2A核心操作；定义所有A2A实现必须支持的基础能力。

3.1 核心操作

3.1.1 SendMessage 发送消息

发起Agent交互的主操作。客户端向Agent发送消息；返回待处理的任务对象，或者直接返回消息响应。

  • 输入：SendMessageRequest 请求对象，携带消息、配置、元数据
  • 输出：二选一：Task任务对象；或者Message直接响应消息（简单交互无需任务追踪）
  • 错误类型：ContentTypeNotSupportedError（媒体类型不支持）、UnsupportedOperationError（任务已终止不能继续发消息）、TaskNotFoundError（任务不存在）
行为说明：Agent可以新建Task异步处理消息；也可以对于简单交互直接返回Message。接口必须立刻返回；如果返回Task，后续处理在后台异步继续执行。

3.1.2 SendStreamingMessage 发送流式消息

与SendMessage逻辑类似，但是处理过程中持续返回实时流式更新。

  • 输出为StreamResponse流：初始返回Task或Message；后续持续推送 TaskStatusUpdateEvent 任务状态事件、TaskArtifactUpdateEvent任务产物更新事件。
  • 两种流模式：纯消息流（只返回一条Message就关闭连接）；任务生命周期流（先返回Task，后续推送事件直到任务进入终止状态）。

3.1.3 GetTask 获取任务

查询已经发起任务的当前状态：状态、产物，可选择携带历史消息。常用于轮询任务状态，或者流式连接断开、收到webhook通知后拉取任务最终结果。

字段类型是否必填说明
tenantstring否透明路由标识，必须与AgentCard选中接口中的tenant保持一致。
idstring是待查询任务ID
historyLengthinteger否返回最近多少条历史消息；0代表不要返回任何历史。

3.1.4 ListTasks 查询任务列表

支持过滤条件、游标分页，批量查询任务，用于多任务的发现与管理。
重要：使用游标分页，而不是offset偏移分页；返回结果按状态更新时间倒序排列。

▶ 点击展开 ListTasks 请求参数字段表
字段类型必填描述
tenantstring否路由租户标识
contextIdstring否按会话上下文过滤任务
statusTaskState否按任务状态过滤
pageSizeinteger否最大返回条数：1‑100；默认最多50条

3.1.5 CancelTask 取消任务

请求终止正在运行的任务。服务端会尝试取消，但不保证一定成功（任务可能已经结束）。返回更新后的Task对象。

错误：TaskNotCancelableError（任务状态不允许取消）、TaskNotFoundError任务不存在。

3.1.6 SubscribeToTask 订阅任务

建立长连接流，接收已有任务的实时更新。不能用于已经进入终止状态的任务。流第一条消息必须返回任务当前快照，防止 GetTask 和订阅之间消息丢失。当任务进入终止状态，流自动关闭。

3.1.7 CreatePushNotificationConfig 创建推送通知配置

为任务配置Webhook回调地址，通过HTTP POST推送异步更新。Agent会向配置URL发送StreamResponse格式负载。该接口只有Agent开启pushNotifications能力才可用。

3.1.8~3.1.10 推送通知配置：获取/列表/删除

GetTaskPushNotificationConfig读取配置；ListTaskPushNotificationConfigs列出任务全部webhook配置；DeleteTaskPushNotificationConfig删除配置，接口具备幂等性。

3.1.11 GetExtendedAgentCard 获取扩展Agent Card

客户端鉴权完成后获取增强版Agent Card。只有AgentCard中 capabilities.extendedAgentCard=true才可以调用；返回经过权限过滤、包含更多私有技能与能力信息的卡片。需要携带合法鉴权凭证。

  • 错误：UnsupportedOperationError 未声明支持该能力；ExtendedAgentCardNotConfiguredError 声明支持但未配置扩展卡片。

3.3.4 能力校验 Capability Validation【目标章节】

Agent会在 AgentCard 中声明自身具备的可选能力。当客户端调用Agent未对外声明支持的接口与特性，Agent必须返回对应的错误响应。
  • 推送通知 Push Notifications
    当 AgentCard.capabilities.pushNotifications 为false或者该字段不存在时，所有推送通知配置操作（创建、查询、列举、删除）必须返回 PushNotificationNotSupportedError。
  • 流式 Streaming
    当 AgentCard.capabilities.streaming 为false或不存在时，调用 SendStreamingMessage 或者 SubscribeToTask，必须返回 UnsupportedOperationError。
  • 扩展Agent Card
    当 AgentCard.capabilities.extendedAgentCard 为false或缺失，调用获取扩展卡片接口，返回 UnsupportedOperationError。
    如果Agent声明支持该能力，但实际没有配置扩展卡片，则返回 ExtendedAgentCardNotConfiguredError。
  • 扩展 Extensions
    如果AgentCard中将某个扩展标记为 required:true，但客户端请求没有声明支持该扩展，Agent必须返回 ExtensionSupportRequiredError。
客户端最佳实践：在调用依赖可选能力的接口之前，优先解析Agent Card，预先校验能力是否支持，避免无效请求。

3.4 多轮交互

A2A依靠contextId上下文ID、taskId任务ID实现多轮对话，维持会话连续性。

  • contextId：逻辑分组多个Task、Message；Agent可以生成contextId，也可以接受客户端传入；客户端不应该随意自行构造contextId。
  • taskId：服务端生成，代表一个状态化任务；客户端不能自定义taskId用于新建任务。

多轮交互模式

  1. 上下文延续：后续消息带上同一个contextId，继续会话；可以携带taskId继续处理现有任务，也可以不带taskId在同一个会话中新建任务。
  2. 输入中断状态 TASK_STATE_INPUT_REQUIRED：Agent需要用户补充信息，任务进入该中断状态；客户端带上原有taskId、contextId发送新消息继续交互。
  3. 引用任务：Message的 referenceTaskIds字段，可以引用一批历史相关任务作为上下文。

3.5 任务更新交付三种机制

模式说明适用场景依赖能力
轮询 Polling(GetTask)客户端周期性调用GetTask拉取状态；实现最简单；会产生多余请求、延迟较高。简单集成、防火墙严格限制长连接环境。无额外能力要求
流式 Streaming长连接，事件实时推送；低延迟；需要保持连接。SendStreamingMessage / SubscribeToTask。交互式应用、实时监控进度。需要 streaming:true
推送通知 Push(Webhook)Agent主动POST到客户端webhook地址；客户端不需要维持长连接；客户端服务需要可被公网访问。服务端‑服务端对接、超长后台任务、事件驱动架构。需要 pushNotifications:true

3.6 协议版本管理

协议版本使用 主版本.次版本(Major.Minor)；补丁版本号不影响协议兼容性，请求头中不要携带补丁版本。

  • 客户端：每次请求带上HTTP Header A2A‑Version: 1.0；如果header为空，服务端默认按0.3版本处理。
  • 服务端：按照客户端请求的Major‑Minor版本语义处理；不支持该版本返回 VersionNotSupportedError；同一个服务可以对外暴露多个不同版本的接口地址。

4. 协议数据模型

A2A使用Protocol Buffers定义标准数据模型；不同协议绑定必须输出语义等价的结构。JSON序列化全部使用驼峰命名camelCase；枚举值保留大写蛇形 SCREAMING_SNAKE_CASE。

4.1 核心对象概览

Task 任务

  • id：任务唯一UUID，服务端生成（必填）
  • contextId：会话上下文ID（可选）
  • status：TaskStatus状态对象（必填），包含state任务状态码、附带message、时间戳timestamp
  • artifacts：产物数组，任务输出结果
  • history：消息历史记录数组
  • metadata：自定义KV元数据

TaskState 任务状态枚举

枚举值含义
TASK_STATE_UNSPECIFIED未知未指定状态
TASK_STATE_SUBMITTED任务已经提交接收确认
TASK_STATE_WORKING正在执行处理
TASK_STATE_COMPLETED执行成功【终止状态】
TASK_STATE_FAILED执行失败【终止状态】
TASK_STATE_CANCELED被取消【终止状态】
TASK_STATE_INPUT_REQUIRED需要用户补充输入【中断状态，非终止】
TASK_STATE_REJECTEDAgent拒绝执行任务【终止状态】
TASK_STATE_AUTH_REQUIRED需要鉴权授权才能继续【中断状态，非终止】

Message消息、Part片段、Artifact产物

  • Message：通信单元，role角色（ROLE_USER / ROLE_AGENT）；messageId消息ID；parts内容片段数组；可携带contextId、taskId、referenceTaskIds引用其他任务。
  • Part：内容片段，oneof互斥字段：text文本 / raw二进制base64 / url远程文件地址 / data结构化JSON数据；附带mediaType媒体MIME类型。必须恰好选择其中一个字段。
  • Artifact：任务输出产物；artifactId唯一ID；parts数组；name、description描述。

4.2 流式事件

  • TaskStatusUpdateEvent：任务状态变更事件；携带taskId、contextId、status对象。
  • TaskArtifactUpdateEvent：产物更新事件；artifact对象；append是否追加模式、lastChunk是否最后分片。

4.3 推送通知对象

Webhook负载是 StreamResponse 对象；只能包含task / message / statusUpdate / artifactUpdate四选一；Agent发送HTTP POST，带上AuthenticationInfo鉴权头；客户端返回2xx代表接收成功。

4.4 AgentCard Agent发现卡片

Agent对外自描述JSON清单；可以通过 well‑known地址 /.well‑known/agent‑card.json 获取。包含名称、描述、supportedInterfaces多协议接口列表、skills技能列表、capabilities能力集合、securitySchemes鉴权方案、输入输出媒体类型。支持JWS签名保证防篡改。

8. Agent发现：Agent Card

  • A2A服务端必须对外提供Agent Card。
  • 标准发现地址：https://域名/.well‑known/agent‑card.json
  • supportedInterfaces数组按优先级排序，第一个为首选接口；选中接口如果设置tenant字段，客户端所有请求必须带上完全相同tenant值。
  • 支持JWS签名，使用RFC8785 JSON规范化JCS算法做签名前序列化，保证签名跨设备一致性。
  • 服务端应当配置Cache‑Control、ETag缓存头，客户端使用条件请求减少重复下载。

13. 安全注意事项（摘要）

  • 生产环境全部传输必须启用TLS加密；HTTP生产环境强制HTTPS，gRPC强制TLS。
  • ListTasks/GetTask所有任务接口必须做鉴权鉴权域隔离，用户只能访问自己有权限的任务，不能泄露其他任务存在与否。
  • Webhook推送安全：服务端校验webhook地址，防御SSRF攻击，禁止回环、内网地址；webhook回调必须带上鉴权凭证；客户端校验回调来源身份；webhook逻辑做好幂等处理，允许重复推送。
  • 扩展AgentCard接口强制鉴权，不能返回敏感内部信息。
  • 全部入参严格校验；限制消息大小、文件大小；做好限流、审计日志。

附录B：A2A与MCP（Model Context Protocol）关系

MCP（Model Context Protocol）：聚焦模型/Agent如何连接工具、API、外部资源；标准化工具描述、函数调用、入参输出；解决Agent调用外部资源的标准。

A2A Agent2Agent Protocol：聚焦独立Agent之间对等通信协同；Agent互相发现能力、委派任务、管理共享任务、交换上下文；解决Agent与Agent之间的伙伴协作、任务委派。

二者互补，可以组合使用：A2A客户端Agent通过A2A把复杂任务委派给远端A2A服务Agent；远端Agent内部，使用MCP协议调用工具、数据源，完成业务逻辑。
